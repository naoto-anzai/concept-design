# 概念を画面にまとめる(画面設計の手法)

製品に依存しない手法。概念設計(概念の集合)から、「どの概念とどの概念を 1 つの画面に入れるか」を決める。
画面の一覧は、この答えから出てくる。実例は `examples/hackathon/groups.yaml`。

**根拠の扱い。** この手法は、概念の独立性・同期・ジャーニーという既存の部品から組み立てた作成者の案(推論)。ジャクソンの著作で、画面設計の手法は確認していない。

## 1. 問い

- 入力: P1(その版)に入れる概念の集合 C。
- 出力: C のグループ分け。1 グループ = 1 画面。
- 範囲は「概念」で決める。入れない概念、未決の概念は、画面を持たない。

## 2. 考え方

1. **概念の組ごとに、同じ画面に入れる度合いを決める。** n 概念なら n(n−1)/2 組。
2. **度合いには、必ず理由を付ける。** 理由は、次のどれかから引く。
   - ジャーニーの同じ歩で、両方を同時に見る・操作する。
   - 同期の `where` が、片方の状態を読んでもう片方を見せる。
   - 呼ぶ人が違う、使う場面が違う(分ける理由)。
3. **分け方を全部数えて、点数を付ける。** 5 概念で 52 通り、8 概念で 4,140 通り。機械で足りる。
4. **候補から、人が選ぶ。** 点数は判断の材料で、決めるのは人。

## 3. 入力(`groups.yaml`)

```yaml
status: proposed             # 提案。チームの合意後に confirmed
concepts: [A, B, C, D]       # この版に入れる概念
shared: [A]                  # 多くの機能が使う中心の概念。画面に閉じず、必要な画面に出す
limits:
  max_concepts_per_screen: 3 # 1 画面の概念数の上限(shared を除く)
pairs:
  - {a: B, b: C, kind: must,   reason: "..."}   # 同じ画面に入れないと用が足りない
  - {a: C, b: D, kind: prefer, reason: "..."}   # 一緒だと画面の行き来が減る
  - {a: B, b: D, kind: apart,  reason: "..."}   # 一緒だと混乱する(呼ぶ人、場面が違う)
  - {a: A, b: D, kind: neutral}                 # どちらでもよい(理由は要らない)
```

| kind | 同じ画面 | 別の画面 | 理由 |
|---|---|---|---|
| must | +3 | 不可 | 必須 |
| prefer | +1 | 点なし(「一緒にできなかった」と報告) | 必須 |
| neutral | 0 | 0 | 不要 |
| apart | 不可 | 0 | 必須 |

- 重みの 3 と 1 は、作成者の置いた値(推論)。変えてよい。
- 中心の概念(`shared`)は、組にしない。ほとんどの機能が使うので、判断の材料にならない。

## 4. 実行と検査

```
python3 tools/screen_groups.py groups.yaml [--top 5] [--concepts concepts.yaml]
```

- ERROR: `concepts` にない名前、kind の誤り、`must`・`prefer`・`apart` の理由の欠け、組の重複。
- WARN: 未記入の組(neutral として数える)。
- 出力: 条件を満たす分け方を、点数の高い順に。同点なら、画面が少なく、一緒にできなかった prefer が少ないもの。
- 上限と must・apart で、条件を満たす分け方が無いときは、そう報告する(入力の矛盾か、上限が厳しい)。

## 5. 使い方の手順

1. 概念ごとに、入れる・入れない・未決を決める(概念で決める)。
2. 中心の概念を `shared` にする。
3. 組ごとに kind と理由を書く(メンバーが直せる)。
4. 実行して、候補を見る。
5. 候補から選び、選んだ理由を `decisions.yaml` 等に残す。

## 6. 限界

- 画面の中の配置、操作の順は決めない(次の段階)。
- 度合いは人が決める。ジャーニーが未記入なら、理由は推論になる。
- 概念を、さらに細かい単位(アクション、状態の読み取り)で分ける場合は、概念の代わりにその単位を `concepts` に書けば、同じ道具が使える。

## 7. 評価基準

出典は、Nielsen「10 Usability Heuristics」(1994)、Shneiderman「Eight Golden Rules」、ISO 9241-11、Card・Moran・Newell の KLM(1980)、Cowan(2001)、Pirolli・Card(1999)、Norman。
どれも指針で、グループ分けの正しさを直接測るものではない。以下は、それらの項目を、このグループ分けの検査に組み替えた作成者の案(推論)。数字は暫定。
**「7±2」(Miller)は使わない**(本人が、7 は偶然の一致かもしれないと書いている)。

| ID | 基準 | 根拠 | 測り方 |
|---|---|---|---|
| A | 入れた概念のアクションが、いずれかの画面から呼べる | 有効さ(ISO 9241-11) | 機械(`screen_check.py --concepts`) |
| B | ジャーニーごとの、画面遷移の回数と操作数 | KLM、効率 | 機械 |
| C | 1 画面の概念数と、状態を変える操作の数 | Cowan(約 4 チャンク)、Hick | 機械 |
| D | 画面をまたいで覚えさせない | Shneiderman 8、Nielsen 6 | 机上(`checklist.md`) |
| E | 操作の結果の状態が見える | Nielsen 1、Norman の評価の溝 | 机上 |
| F | ジャーニーの終点で、完了が分かる | Shneiderman 4 | 机上 |
| G | 状態を変える操作に、戻す操作がある | Shneiderman 6、Nielsen 3 | 機械 |
| H | 画面に、その歩に要らないものがない | Nielsen 8 | 机上 |
| I | 同じ概念は、どの画面でも同じ見せ方 | Nielsen 4、Shneiderman 1 | 机上 |
| J | 概念の仕様に、画面の語を書かない | Jackson の「UI 結合」(早見表の項目名のみ確認) | 機械(既存の lint) |
| K | 最初のタップが、狙いと合う | Pirolli・Card の情報の手がかり | 人に試す |

進め方は、skill `screen-design`(`.claude/skills/screen-design/`)の 6 ステップ。
