## 1. 演繹的な説明: 2 つの原則から、項目が出てくるまで

この章は、前提から順に、項目が 1 つずつ必要になる理由を示す。次の 2 章(全体図と項目ごとの説明)の内容は、この章の順序で組み直したものではなく、同じ項目を別の角度から見たもの。

読み方: 各段は「前提 → そこから言えること → 新しく出てくる項目」の順に書く。段の番号が上がるほど、項目が細かくなる。前の段で出ていない項目は、後の段の前提に使わない。

### 段の全体

```
段 0  出発点     機能を、価値のある単位で、変えやすい部品に分けたい
  │
段 1  2 つの原則  部品は 1 つの目的を持つ / 部品は互いを知らない
  │              └→ 出力は 2 種類: 概念 と 同期
  │
段 2  概念の芯    目的、名前
  │
段 3  概念の中身  状態、アクション、運用原則(筋)、登場する人
  │
段 4  独立の保ち方  型パラメータ
  │
段 5  アクションの中身  引数、requires、effects、system
  │
段 6  同期の中身  when、then、where
  │
段 7  全体の規則  必須・禁止・置換(C1〜C5)
  │
段 8  入力     ここまでの項目のうち、人に聞かないと決まらないもの
```

### 段 0: 出発点

- 前提: 作るものは、機能の集まりである。機能は、利用者にとっての価値(`input.yaml` の `value`)の単位である。
- 目指すこと: 機能を、作りやすく、変えやすい部品に分ける。
- ここではまだ、項目は出てこない。

### 段 1: 2 つの原則から、出力の種類が決まる

- 前提(原則 1): 部品(概念)は、1 つの目的だけを持つ。
- 前提(原則 2): 概念は、他の概念の名前・アクション・状態を知らない(独立。C2)。
- 言えること 1: 原則 2 により、概念の中には、他の概念とのつながりを書けない。
- 言えること 2: ところが、1 つの機能は、複数の概念が協力して実現する。つながりは、どこかに書かなければならない。
- 結論: つながりは、概念の外に書く。これが**同期**である。依存の向きは「要求 → 同期 → 概念」の一方向になり、「概念 → 概念」は無い。
- 出てくる項目: **概念**(原則 1 の部品)と、**同期**(原則 2 で追い出したつながり)。出力は、この 2 種類で全部。

### 段 2: 概念を 1 つ決める(芯)

- 前提: 概念は、1 つの目的を持つ(段 1、原則 1)。
- 言えること: 目的が無ければ、何のための部品か決まらない。目的は、「誰の、どんな必要に応えるか」で書く。
- 出てくる項目: **目的**。
- 言えること: 目的が 1 つなので、概念を指す呼び名も 1 つで足りる。既知の概念の名前なら、説明なしで通じる。
- 出てくる項目: **名前**。

### 段 3: 目的を果たす最小の仕組み

- 前提: 概念には目的がある(段 2)。目的を果たすには、何かを覚えておき、それを変える出来事が起きなければならない。
- 出てくる項目: **状態**(覚えておくこと)と、**アクション**(起こせる出来事)。
- 前提: 状態とアクションを並べても、目的が本当に果たされるかは、読む人に分からない。
- 言えること: 目的が果たされる典型の流れを、短い物語で示せば、確かめられる。
- 出てくる項目: **運用原則(筋)**。
- 言えること: 物語には、登場する人が要る。誰が準備し、誰が使うかは、物語の前提になる。
- 出てくる項目: **運用原則(登場する人)**。
- 補足: 運用原則は、アクションと状態を使って書く。段 3 の中では、状態とアクション → 運用原則の順に決まる。

### 段 4: 他の概念の名前を書かずに、渡されるものを扱う

- 前提(段 3 から): アクションは、引数を受け取り、状態を変え、必要なら戻り値を返す関数である。

**言えること 1: 引数や戻り値の型に出てくる名前は、2 種類に分かれる**

```ts
concept Place {
  register(name: String, kind: Kind, location: Point, description: String): Place
  update(place: Place, ...): void
}

concept Congestion {
  report(item: ???, level: Level): void
}
```

- `String`、`Kind`、`Point`、`Level` は、組み込みか、その概念の中で決めた値の型である。
- `Place` は、`register` が新しく作って返す。種類は `Place` 概念の中で決まる。`update(place: Place)` に出てくるのは、`register` が作ったものを渡しているだけである。
- `report` の `item` は、`Congestion` が作るものではない。他の概念が作ったものが、引数として渡される。

**言えること 2: この概念の仕様に、`item` の種類は要らない**

- `Congestion` に必要なのは、「項目を 1 つ指すと、混雑度が 1 つ分かる」ことだけである。項目が場所でも企画でも、仕様は変わらない。

**言えること 3: ただし、`item` の型を、他の概念の名前では書けない**

- `item: Place` と書けば、`Congestion` の仕様に `Place` が出る。独立の原則(段 1)に反する。
- だから、型には、仮の名前を書くしかない。

**結論: 型パラメータ**

```ts
concept Congestion<Item> {
  report(item: Item, level: Level): void
}
```

- `Item` が、型パラメータである。概念の名前の後ろに `<Item>` と書く。
- 型パラメータは、名前だけである。`Item` が何を指すかは、この概念のどこにも書かない。
- 出てくる項目: **型パラメータ**。

**見分け方**

引数や戻り値の型に出てくる名前のうち、その概念のアクションが新しく作らないものが、型パラメータになる。

| 型 | 新しく作るアクション | 型パラメータ |
|---|---|---|
| `Place` | `register` が作る | 不要 |
| `Item`(`Search`、`Destination`、`Congestion`) | 無い | 要る |
| `Label`(`Labeling`) | 無い(`define(label: Label)` は、渡されたものを受け取るだけ) | 要る |

- 「新しく作るか」は、関数の型だけでは決まらない。`effects` の文(「新しい Place を作り」)で決まる。たとえば `Search.query` の戻り値に `Item[]` が出るが、既にあるものを返すだけで、作っていない。

**`Item` が何を指すかは、いつ決まるか**

- 概念の中には書けないので、概念の外で決まる。定義書には、決める場所の記述が無い。
- 作成者の推論: 同期は、`Place` と `Search` の両方の名前を書ける唯一の場所である。そこで、次のように呼び出しを書けば、`Item = Place` が決まる(段 6)。

```ts
sync register-indexes {
  when  Place.register(...) → place
  then  Search<Place>.index(item: place, text: place.name)
}
```

- この書式は、まだ決まっていない案である(型の当てはめを書く場所は未決)。

### 段 5: アクションを細かくする

- 前提: アクションは、状態を変える出来事である(段 3)。
- 言えること 1: 呼ぶときに渡すものが要る。→ **名前・引数**。
- 言えること 2: どんなときでも呼べると、状態の約束(不変条件)が壊れる。呼んでよい条件が要る。→ **requires**。無ければ「なし」と書く(書き忘れと区別するため)。
- 言えること 3: 呼んだ結果、状態がどう変わるかが決まっていなければ、実装もテストもできない。→ **effects**。
- 言えること 4: 出来事には、人が起こすものと、システムが自発的に起こすものがある。区別しないと、サーバー側の処理が要るか分からない。→ **system**(あり / なし)。

### 段 6: 同期を細かくする

- 前提: 同期は、概念どうしをつなぐ(段 1)。つなぐには、「何が起きたら」「何を呼ぶか」が要る。
- 言えること 1: きっかけが要る。きっかけは、利用者の要求か、概念のアクションが完了したこと。→ **when**。
- 言えること 2: 呼ぶ先が要る。呼べるのは、概念のアクションだけ。→ **then**。
- 言えること 3: 「誰が実行してよいか(権限)」は、概念に書けない(独立。段 1)。状態の条件も、他の概念の状態にまたがる。どちらも、同期の側に置くしかない。→ **where**(無い同期もある)。

### 段 7: 全体の規則

段 1〜6 から、次の規則が導かれる。

| 規則 | どの段から | 内容 |
|---|---|---|
| C1 形式 | 段 3、5 | 各概念が、必要な要素をすべて持つ(事前条件が無くても「なし」と書く) |
| C2 独立性 | 段 1 | 概念が、他の概念の名前・アクション・状態を参照しない |
| C3 被覆 | 段 0、1 | すべての機能が、概念と同期の組で実現される。どの機能にも使われない概念は作らない |
| C4 参照の実在 | 段 6 | 同期が指すアクションは、実在する概念のアクション |
| C5 整合 | 段 5 | 各アクションが、不変条件を保つ(人が推論する) |

### 段 8: 入力が要る所

- 前提: 段 2〜6 の項目の中には、他の項目から決められず、現実の事実やチームの選択を聞かないと決まらないものがある。
- それらを、項目ごとに挙げる。

| 項目 | 聞くこと | 未決事項 |
|---|---|---|
| 目的 | 誰が、何を必要としているか | |
| 運用原則(登場する人) | 準備する側、使う側は誰か | OQ-1 |
| アクション | その操作を作るか(作る範囲) | OQ-2 |
| `where` | 権限(役割ごとに何を許すか) | OQ-1、OQ-5 |
| 状態 | 選べる値と、その数 | OQ-4 |
| `requires` | 現実のルール(してはいけない条件、境目の数値) | OQ-4 |
| `system` | 人が関わらずに起きてほしいこと | |

- 言えること: 概念設計を始める前に集める入力は、この 7 つ。残りは、判断(設計する側が評価基準で選ぶ)か、帰結(他が決まれば 1 通りに決まる)である。

## 3. 項目ごとの説明

評価基準の略語: 制約は C1 形式、C2 独立性、C3 被覆、C4 参照の実在、C5 整合。目標は、特定性、分離、完全性、汎用性、なじみ、最小性、単純さ。

### 概念の仕様

#### 名前
- 目的: 概念を指し示す呼び名になる。既知の名前なら、説明なしで通じる。
- 設定: 既知の概念の名前を使う。他の概念の型を名指ししない。
- 評価基準: なじみ(既知の概念で足りるのに、新しい名前を作っていないか)、汎用性(アプリ固有の語でないか)。

#### 型パラメータ
- 目的: 概念が扱う項目のデータ型に、仮の名前(`Item` など)を付けて、他の概念の名前を仕様に書かずに済ませる。型の中身は、同期が決める。プログラミングのジェネリクス(`List<T>` の `T`)にあたる。アクションの引数(値)とは別のもの。
- 例: `Search [Item]` の `Item` は、「場所」や「企画」を入れられる型の穴。概念は、Item が区別できることと、文字列を結びつけられることしか知らない。
- 設定: 他の概念の型を名指ししない。
- 評価基準: 汎用性(対象を替えても成り立つか)、C2。

#### 目的
- 目的: 誰のどんな必要に応えるかを述べる。特定性・分離・完全性は、すべてこの目的を単位に測る。
- 設定: アプリ固有の語や、他の概念の名前で書かない。入力の `value` と利害関係者に結びつける(A1)。
- 評価基準: 特定性(目的と概念が 1 対 1)、分離、完全性。

#### 運用原則
- 目的: 目的が果たされる典型的な流れを示す。テストの筋書きになる。
- 設定: 端の場合ではなく典型を書く。UI やアプリ全体に触れない。短い物語 1 つ。
- 評価基準: 目的を果たす流れになっているか、単純さ。

#### 状態
- 目的: 概念が覚えていることを定め、事前・事後条件を書く土台にする。
- 設定: 集合と二項関係で書く。アクションに足りるだけ書く。表やクラスに寄せない。
- 評価基準: 最小性(どのアクションにも使われない状態が無いか)、完全性(アクションの効果を表せるか)。

#### アクション(名前・引数)
- 目的: 起こせる出来事を一覧にして、概念の振る舞いの範囲を決める。
- 設定: UI に依存しない(「ボタンを押す」と書かない)。システムが自発的に行うものは区別する。
- 評価基準: 最小性(不可欠なものだけか)、完全性(1 つの関心の振る舞いを、この概念がすべて持つか)。

#### `requires`
- 目的: 実行してよい条件を定めて、不変条件を壊す呼び出しを除く。
- 設定: すべてのアクションに書く。無ければ「なし」と書く。文でよい。
- 評価基準: C5(各アクションが不変条件を保つか。人が推論する)、C2。

#### `effects`
- 目的: 実行後に状態がどう変わるかを定める。実装とテストの期待値になる。
- 設定: 状態の語で書く。アルゴリズムや内部の手順は書かない。
- 評価基準: C5、状態に無いものに触れていないか。

#### `system`
- 目的: 人が関わらずに起きる出来事を区別して、サーバー側の処理が要るかを示す。
- 設定: システムが自発的に行うアクションに付ける。
- 評価基準: 最小性(目的に要るものだけか)、分離(人が起こすアクションと混ざっていないか)。

### 同期

#### `when`
- 目的: いつ動くかを決めて、概念を変えずに、要求や他の概念の出来事につなぐ。
- 設定: 完了したアクションを指す。利用者の要求は `Request` のアクションとして書く。
- 評価基準: C4(参照先が実在するか)、C3(機能が実現されるか)。

#### `where`
- 目的: 実行してよい条件(権限、状態の条件)を、概念の外に置く。
- 設定: 権限は同期に書く(A6)。網羅は不要で、本質的なものと種類ごとの代表例を押さえる。
- 評価基準: C2(概念に呼び出し元を書いていないか)、C4、最小性。

#### `then`
- 目的: 続けて呼ぶアクションを指定する。
- 設定: 呼べるのは、概念のアクションだけ。
- 評価基準: C4、C3。

## 4. 見て分かること

- **目的の項目だけが、他の評価の物差しになっている。** 特定性・分離・完全性は目的を単位に測るので、目的の切り方を変えると、同じ設計が違反にも適合にもなる。定義書の A1 が「最も重い曖昧さ」とするのは、このため。
- **文章型の項目(目的、運用原則、`requires`、`effects`)は、機械で確かめられる基準が少ない。** C5 は人が推論するので、評価が人に依存する。
- **評価基準は、軸ごとに偏っている。** ② 依存の向きは C2・C4 が中心で機械的に確かめられる。① 配置は目標(特定性・分離・完全性)が中心で、判断が要る。
- **入力は 7 つ、判断は 5 つ、帰結は 7 つ。** 概念設計を始める前に集める必要があるのは、入力の 7 つだけ。

## 5. 未確認のこと

- 1 章の演繹の順序(段 0〜8)は、作成者が項目の依存関係を整理した順序で、定義書の記述順ではない。特に、段 3 の「運用原則は状態とアクションを使って書く」、段 6 の「状態の条件は同期の `where` に置く」は、定義書の記述と照らして確認していない。
- 型パラメータを何に当てるか(束縛)を、どこに書くかは未決。同期の引数に書く案と、概念ごとの一覧にする案がある。`Labeling` の `Label` は、当てる先が推測できない。
- 3 軸への振り分けは未合意。`system`(自動で起きること)は ③ 書き方に置いたが、「いつ何が実行するか」という ① 配置の問題とも読める。
- 3 分類(入力・判断・帰結)と 3 タイプ(単一・複数・文章)の付け方は、作成者の提案で、チームの確認を受けていない。
- 項目ごとの評価基準の対応づけは、定義書の 7.1 と 6.3 を元にした作成者の整理で、定義書そのものの記述ではない。
