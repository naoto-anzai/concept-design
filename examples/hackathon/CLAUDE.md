# concept-design での作業の決まり

このフォルダは、概念設計(ダニエル・ジャクソン流)から、ジャーニーと API の仕様までを進める作業場。
全体の流れとファイルの役割は README.md にある。写像 `g` の定義は docs/decision-map.md にある。判断に迷ったら定義に従い、食い違いは利用者に報告する。

## 守ること

1. **編集の前に `make lint` を実行し、編集の後にもう一度実行する。** ERROR を残さない。
2. **概念の仕様に、他の概念の名前・UI の語・技術の名前を書かない。** つながりと権限は同期に書く。
3. **工数や実装の都合で、概念の独立性を崩さない。** 統合してよいのは、目的が同じ概念だけ。
4. **分割・統合・採否の判断は、`decisions.yaml` に残す。** 捨てた案と理由も残す。
5. **未決のことは決めない。推測で埋めず、`open-questions.yaml` に載せ、該当の箇所に `OQ-n` を付ける。** 決めるのはチーム。
6. **画像などから起こした値には、★要確認 を付ける。** 確認が取れるまで、確定として扱わない。
7. **`api/actions.generated.md` は導出結果。手で編集しない。** `journey/*.md` は育てる文書。`--force` で上書きしない(利用者の書き込みが消える)。
8. **評価基準は、測れる形で書く。** 「使いやすい」ではなく、操作数・所要時間・観察で確かめられる条件にする。
9. **提案と合意を区別する。** 作成者の提案は status: proposed、チームの合意後に confirmed。
10. **commit / push は依頼されたときだけ。**

## 量のある作業

対象が多い作業(多数の機能の書き起こしなど)は、`~/.claude/CLAUDE.md` の規則に従って Codex に任せる。
概念の分け方の判断、同期の設計、候補の比較は、自分で行う。
