# 意思決定写像: 概念設計

作成日: 2026-11-12

## 0. この文書の位置づけ

- これは写像 `g`(概念設計)の定義である。特定のアプリの答えではない。
- 既存の写像 `f`(型構成の決定。`shiftManager/意思決定写像.md`)は、概念の集合を入力に取る。`g` はその一つ手前に置く。
- 重きを置くのは「形式」である。`g` の入力と出力がどんな形をしていれば、前後の写像とつながるかを決める。
- 根拠は 6.1040(Fall 2025)と 6.170(Spring 2013)の日本語訳である。訳は `~/projects/webAppDesign/courses/` にあり、この文書の原本も同じプロジェクトの `notes/curated/` にある。出典は「科目 ファイル名(節)」で示す。資料に無い内容は「資料外」と書く。
- 出典の大半は、サブエージェントが資料から抜き出したものである。私が原文で確認したのは、「確認済み」と付けた 3 点だけである。引用して発表に使う前に、該当箇所を原文で確かめること。

```
g : 入力(問題記述 + 機能の集合)
      ──[設定 = 仕様の形式と独立性の規則で制約]──▶ 出力(概念の集合 + 同期の集合)
                              評価基準 = { 制約(満たすか否か), 目標(より良いか) }
```

## 1. 結論

1. **入力は「機能(feature)」の粒度で渡す。** 課題そのままでも、機能の原子でもない。
2. **機能の原子に当たるのが概念である。** 原子への分解は `g` が行う判断そのものなので、入力で済ませてはいけない。
3. **出力は「概念の仕様 + 同期」である。** 6.1040 の標準形式をそのまま使えば、`f` の入力テンプレートとほぼ一致する。ずれは 3 点ある(8.2)。
4. **最も曖昧なのは「1 つの関心」の大きさである。** 評価基準(分離・完全性・特定性)は、どれも目的(purpose)を単位にして測る。その目的の粒度を決める規則が、資料に無い(7 章)。
5. **詰める水準は、次の写像が決める。** 次の写像の出力を変える情報だけを書き、変えない情報は書かない(8 章)。

## 2. 写像の連鎖の中での位置

開発を写像の連鎖と見ると、6.1040 の課題の順序は次のように並ぶ。

| 写像 | 決めること | 入力 | 出力 | 主な評価基準 | 出典 |
|---|---|---|---|---|---|
| `p` 問題設定 | どの問題を解くか | 領域 | 問題記述 | 需要が本物か、証拠があるか | 6.1040 assignment-1、problem-framing |
| `q` 機能の選択 | 何を提供するか | 問題記述 | 機能(最大 3 つ) | 問題を和らげるか、価値 | 6.1040 assignment-1・2(ピッチ) |
| **`g` 概念設計** | **どう分けるか** | **問題記述 + 機能** | **概念 + 同期** | **モジュール性** | 6.1040 assignment-2、L02〜L04 |
| `h` 技術の選択 | 何で作るか | 概念の案 + 同期 + 規模・条件 | 案 × 技術基盤の候補 | 工数、既製の割合、リスク(10 章) | 資料外 |
| `f` 型構成の決定 | どう動かすか | 概念 + 同期 + 規模 | 構成 + 設計詳細 + 工数 | コスト、開発工数 | shiftManager/意思決定写像.md |

この並びから、写像を切る規則が 2 つ導ける。

- **1 つの写像は、1 種類の評価基準で 1 種類のことを決める。** `q` は価値で決め、`g` はモジュール性で決める。2 つを 1 つの写像にまとめると、評価基準が混ざり、どちらの理由で選んだのかを説明できなくなる。これは関心の分離(separation of concerns)を工程に当てはめたものである。
- **前の写像の出力の形式は、次の写像の入力の形式と一致させる。** 一致しない部分は、変換の規則を書くか、どちらかの形式を直す。

資料は、この並びが一方向でないことも述べている。問題と解は互いに影響して変わる(6.170 講義 55 s16)。実装の段階で設計を変えてよいが、仕様をコードと一致させ、変更の理由を記録する(6.1040 assignment-2 の助言、assignment-4a)。したがって各写像は、後の写像から差し戻されたときに、同じ手順でやり直せる形にしておく。

## 3. 目的

機能の集合を、独立に設計・実装・説明できる振る舞いの単位(概念)の集合と、その間の同期に分けること。

この目的は、次の 2 つの記述から導かれる。

- 機能と概念は別のものである。「概念とは、アプリを構成する、ユーザーに見える機能の構成要素(building bricks)である。機能とは、複数の概念が組み合わさって特定のニーズに対処する価値をもたらすときに、ユーザーが体験するものである」(6.1040 assignment-2 の助言「概念と機能の違い」。確認済み)。
- 概念の質は、使いやすさ・保守性・信頼性を同時に左右する。弱い概念は「使いにくい、保守が混乱する、信頼できない」。強い概念は「直感的で予測可能、分離と局所化、より信頼できる」(6.170 講義 26 s9-10)。

「どの機能を作るか」は目的に含めない。それは `q` の目的である。

## 4. 設定(前提)

写像の中で選び直さないものを置く。

| 区分 | 内容 | 出典 |
|---|---|---|
| 仕様の形式 | 概念は、名前・目的・原理・状態・アクションで書く(6.1) | 6.1040 L02 |
| 同期の形式 | `when … where … then …` で書く(6.2) | 6.1040 L02、problem-set-2 |
| アプリの構造 | アプリ = 概念の一覧 + 同期の一覧。入れ子にしない | 6.1040 understanding-synchronizations |
| 独立性の規則 | 概念は、他の概念のアクションを呼ばない。他の概念の状態を読み書きしない。複合オブジェクトを共有しない | 6.1040 L02 |
| UI に依存しない | アクションは「ボタンを押す」ではない。画面の配置や遷移を書かない | 6.1040 L02、L03 |
| 表現に依存しない | 状態は集合と関係で書く。クラス・表・ドキュメントのどれにも寄せない | 6.1040 L02、L03 |
| 再利用の元 | 既知の概念(認証、投票、通知など)を先に探す | 6.1040 L02、L04 / 6.170 講義 29 s2 |
| 個数の目安 | 概念は 3〜5 個。課題の規模に対する目安で、規則ではない | 6.1040 assignment-2(確認済み) |

「表現に依存しない」は、次の写像との関係で重要である。技術基盤を何にするかは、`g` の設定に入らない。したがって `g` の出力は、技術基盤を変えても変わらない。6.170 も「1 つのモデル、多数の実装」と述べている(講義 24 s3)。

資料外の設定を 1 つ加える案がある。実装主体(人か、どの水準の AI か)である。6.1040 は、概念が独立なので AI に渡す文脈は 1 つの概念の仕様だけで足りる、と述べている(assignment-4a)。実装主体の能力が低いほど、1 つの概念を小さく保つ理由が強くなる。ただし、これを `g` の設定に入れると、技術に依存しないという性質が弱まる。入れる場合は、評価基準の重みとして扱い、制約にはしない。

## 5. 入力

### 5.1 入力の粒度は、3 つの候補から選ぶ

| 候補 | 中身 | 判定 | 理由 |
|---|---|---|---|
| A 課題そのまま | 問題記述だけ | 不可 | 「何を作るか」と「どう分けるか」を同時に決めることになる。評価基準が 2 種類になり、出力集合も広がりすぎる |
| **B 機能** | **問題記述 + 機能の集合** | **採用** | 資料が指定する形である。価値の単位が決まっていて、構造はまだ決まっていない |
| C 機能の原子 | 操作の一覧、画面の一覧など | 不可 | 原子への分解は `g` の判断である。入力で済ませると、モジュール性の評価を通さずに構造が決まる |

B を採る根拠は、6.1040 の課題 2 の構成である。概念設計の前に置かれる成果物は、問題記述と、主要な機能を最大 3 つ含むピッチである(assignment-2。確認済み)。課題 1 も「問題を特定し、いくつかの機能を提案することのみ」とし、設計は次の課題に回している(assignment-1 の概要)。

C が不可である理由は、機能と概念が 1 対 1 に対応しないことから導かれる。資料の例では、ウィッシュリストという 1 つの機能が、4 つの概念(ウィッシュリスト、配信状況、契約、通知)で実現される(assignment-2 の助言。確認済み)。逆に、通知という 1 つの概念は、複数の機能で使われる。機能を先に原子へ割ると、通知が機能ごとに別々の原子として現れ、冗長性(1 つの目的に 2 つ以上の概念)を入力の段階で作ることになる。

6.170 も同じ区別をしている。機能は「互いに関連するアクション」で「より大きな目的のためのもの」であり、「アクションを列挙するだけで機能にまとめない」のは誤りとされる(講義 50 s17)。

### 5.2 入力が満たすべき性質

| 番号 | 性質 | 理由 | 資料の根拠 |
|---|---|---|---|
| I1 | 各機能は、価値の単位である。利用者が得るものを 1 つ述べる | 概念の目的は、利害関係者にとっての価値として書く。機能から価値をたどれないと、目的が書けない | 6.1040 L03、assignment-2 |
| I2 | 各機能は、問題と利害関係者に結びつく | 目的の出どころを示すため。結びつかない機能は `q` に差し戻す | 6.1040 assignment-2(機能の説明に含める項目) |
| I3 | UI を含まない | アクションは UI に依存しない。入力に UI があると、UI の手順がそのままアクションになる | 6.1040 L02、L03 |
| I4 | 技術を含まない | 4 章の設定による | 6.1040 L02 |
| I5 | 機能ごとに外せる | 後の写像が、機能の有無による差を計算できるようにする | 資料外(`f` の 3.3 が、通知の有無を概念集合の差として扱うことからの要請) |
| I6 | 問題は、解決策から独立に書かれている | 「問題とは、特定の解決策とは独立なドメインにおいてユーザーが経験する困難」 | 6.1040 assignment-1 |

I5 は、I1 が満たされていれば自然に満たされる。価値の単位で切ってあれば、機能を外すことは価値を 1 つ諦めることに対応する。

### 5.3 任意の入力: 典型的な場面

各機能に、典型的な場面を 1 つ添えると、アクションを取り出しやすくなる。概念に書く細部は「ユーザーのステップ、システムの応答、ユーザーが与え・受け取るデータ」だからである(6.1040 L03)。

ただし、これは資料の指定ではない。6.1040 では、ユーザージャーニーは概念設計の後に書かせている(assignment-2 の提出物の順)。場面から概念を取り出す手順も、資料に記述が無い。場面を入力に入れる場合は、I3 を守り、画面の操作ではなく「誰が何をして、何が返るか」の水準で書く。

### 5.4 入力テンプレート

```yaml
problem:
  domain: ""
  statement: ""              # 解決策から独立に書く(I6)
  stakeholders:
    - { name: "", role: "", impact: "" }   # role は後の写像で権限と規模に使う
  evidence: []               # 根拠・比較対象
features:                    # 最大 3 つ程度。各機能は価値の単位(I1)
  - name: ""
    value: ""                # 誰の、どの必要に応えるか(I2)
    stakeholders: []         # problem.stakeholders の name を参照
    scenario: ""             # 任意。UI を含めない(5.3)
    optional: false          # 外して比べたい機能は true(I5)
passthrough:                 # g は使わない。後の写像へそのまま渡す
  scale: {}                  # 利用者数など
  constraints: {}            # 予算、期限、実装主体、運用する人
  tech_preferences: {}       # 経験のある技術、使ってみたい技術、避けたい技術
```

`passthrough` を設けるのは、`g` が使わない情報を連鎖の途中で失わないためである。規模や予算は、モジュール性の判断には使わない。しかし `f` は規模を入力に取る。`g` の入力に置き場所が無いと、`f` の手前で改めて集めることになる。

## 6. 出力集合

### 6.1 出力の要素: 概念の仕様

| 要素 | 書くこと | 書き方の規則 |
|---|---|---|
| 名前 | 概念の名前と型パラメータ。例: `Upvoting [User, Item]` | 既知の概念の名前を使う。他の概念の型を名指ししない |
| 目的 | 誰のどんな必要に応えるか | アプリ固有の語や、他の概念の名前で書かない |
| 原理 | 目的が果たされる典型的な流れ | 端の場合ではなく典型を書く。UI やアプリ全体に触れない |
| 状態 | 概念が覚えていること | 集合と二項関係で書く。アクションに足りるだけ書く |
| アクション | 状態を変える操作 | 各アクションに `requires`(事前条件)と `effects`(事後条件)を書く。システムが自発的に行うものは `system` と付ける |
| 注記 | 自明でない判断と、その理由 | 仕様の本体には入れない |

出典: 6.1040 L02、L03、concept-modularity、problem-set-2、final-project-main。

### 6.2 出力の要素: 同期

形式は `when 概念A.アクション(...) where 状態の条件 then 概念B.アクション(...)` である。`when` は完了したアクション、`then` は呼び出すアクションを指す。利用者からの要求は、`Request` という擬似的な概念のアクションとして書く(6.1040 L02、problem-set-2、understanding-synchronizations)。

概念どうしのつながりは、すべて同期に書く。概念の中には書かない。これは独立性の規則(4 章)から導かれる。

### 6.3 出力集合の定義

出力集合は、次の制約をすべて満たす(概念の集合, 同期の集合)の組の全体である。

| 番号 | 制約 | 確かめ方 |
|---|---|---|
| C1 形式 | 各概念が 6.1 の要素を持つ。各同期が 6.2 の形式に従う | 機械的に確かめられる |
| C2 独立性 | 概念の仕様に、他の概念の名前・型・アクションが現れない | 機械的に確かめられる |
| C3 被覆 | すべての機能が、概念と同期の組で実現される | 対応表(6.4)で確かめる |
| C4 参照の実在 | 同期が参照する概念とアクションが実在する | 機械的に確かめられる |
| C5 整合 | 各アクションが不変条件を保つ | 人が推論する(6.1040 L03) |

### 6.4 出力に加える対応表(資料外の提案)

機能と概念の対応表を、出力に含めることを提案する。

| | 概念1 | 概念2 | 概念3 | 同期 |
|---|---|---|---|---|
| 機能1 | ○ | ○ | | s1 |
| 機能2 | | ○ | ○ | s2, s3 |

この表は 3 つの役に立つ。

- C3(被覆)を確かめられる。空の行は、実現されていない機能である。
- 空の列は、どの機能にも使われない概念である。最小性に反する。
- 機能を外したとき(I5)、どの概念と同期が要らなくなるかが分かる。`f` の「通知なし」の計算は、これを使う。

資料は、この表を求めていない。6.1040 が求めるのは、概念の役割を説明する半ページ以内の注記である(assignment-2)。

    purpose: ""

    state: ""                # 集合と関係

## 7. 評価基準

### 7.1 制約と目標を分ける

評価基準は 2 種類に分かれる。制約は、満たさない出力を除く。目標は、残った出力の中で優劣を付ける。

制約は 6.3 の C1〜C5 である。目標は次のとおり。

| 目標 | 意味 | 違反の名前 | 出典 |
|---|---|---|---|
| 特定性(specificity) | 目的と概念が 1 対 1 | 冗長性(1 つの目的に 2 つ以上の概念)、過負荷(1 つの概念に 2 つ以上の目的) | 6.1040 L04(確認済み) |
| 分離(separation) | 無関係な関心を 1 つの概念に混ぜない | 混同(conflation) | 6.1040 L04 |
| 完全性(completeness) | 1 つの関心の振る舞いを、1 つの概念がすべて持つ | 断片化(fragmentation) | 6.1040 L04 |
| 汎用性(genericity) | アプリ固有でない | アプリ固有の語、非ジェネリックな型 | 6.1040 L02、concept-modularity |
| なじみ(familiarity) | 既知の概念を使う | 身近な概念で果たせる目的に、新しい概念を作る | 6.1040 L04、assignment-2 の採点基準 |
| 最小性 | 不可欠な概念とアクションだけ | 使われない概念、些細な詳細 | 6.1040 final-project-outline / 6.170 講義 50 s13 |
| 単純さ | より単純で、より一般的 | 粗削りな点、複雑な点 | 6.170 講義 28 s3、s6-7 |

### 7.2 分割と統合は、目標の違反から決まる

概念の案を分割するか統合するかは、どの目標に違反しているかで決まる。

| 違反 | 操作 | 結果 |
|---|---|---|
| 過負荷、混同 | 分割する | 目的ごとに 1 つの概念になる |
| 冗長性、断片化 | 統合する | 1 つの目的を 1 つの概念が持つ |
| アプリ固有 | 一般化する | 型パラメータを導入する |
| 既知の概念で足りる | 置き換える | 既知の概念を使う |
| どの機能にも使われない | 削除する | 概念が減る |
| 概念が他の概念を参照する | 同期に出す | つながりが同期に移る |

分割と統合は、逆向きの操作である。どちらを当てるかは、目的を数えれば決まる。1 つの概念に目的が 2 つあれば分割し、1 つの目的に概念が 2 つあれば統合する。

この操作の繰り返しは、6.170 の「概念設計ループ」に当たる。発明/再考、概念設計、展開/評価、単純化/一般化の 4 つを回す(講義 28 s2)。

したがって、「案を出す」ことと「分割・統合する」ことは、別の写像にしない。目的・評価基準・出力集合が同じだからである。違うのは手順だけなので、`g` の中の 2 つの段として扱う(9 章)。

## 8. 曖昧な部分と、詰める水準

### 8.1 写像として見たときの曖昧な部分

| 番号 | 曖昧な部分 | なぜ問題か | 対処 |
|---|---|---|---|
| A1 | 「1 つの関心」「1 つの目的」の大きさ | 特定性・分離・完全性は、目的を単位に測る。目的は出力の一部なので、目的の切り方を変えれば、同じ設計が違反にも適合にもなる | 目的を、入力の `value`(誰のどの必要か)と既知の概念に結びつけて固定する。結びつかない目的は認めない |
| A2 | 「機能」の大きさ | 資料の指定は「名前と数文」だけである。大きすぎれば候補 A に、小さすぎれば候補 C に近づく | 1 つの機能は 1 つの必要に応え、1 つの場面で語れる大きさにする(5.2 の I1、5.3) |
| A3 | 目標の重み | 目標どうしがぶつかる。例: 汎用性を上げると、原理が抽象的になり分かりにくくなる | 重みは写像の中で決めない。設定で決めるか、複数の案を残して次の写像に渡す(9 章の手順 6) |
| A4 | 機能から概念を見つける手順 | 資料に手順が無い。`g` は関数ではなく、探索である | 既知の概念から探し、足りない分だけ作る。6.170 は見つけるための問いを挙げる(講義 27 s4) |
| A5 | 概念と同期の境界 | 同じ振る舞いを、概念のアクションにも同期にも書ける | 2 つ以上の概念にまたがる振る舞いは同期に書く。独立性の規則から決まる |
| A6 | 権限の置き場所 | 「誰がそのアクションを呼べるか」を、概念に書くか同期に書くか | 同期に書く。6.1040 は、アクセス制御を同期の代表例に挙げる(assignment-2。確認済み) |
| A7 | 規模や性能の扱い | `g` は使わないが、後の写像は使う | `passthrough` で渡す(5.4) |
| A8 | 2 つの版の形式の違い | 6.170(2013)には、目的・原理・状態・アクションの形式が無い。概念は「設計問題に対する解決策」で、問題・解決策・例・洗練・オブジェクトモデルで書く(講義 27 s4、29 s3) | 形式は 6.1040 に従う。6.170 は、動機と、分割・統合の例として使う |

A1 が最も重い。評価基準が、出力に含まれる目的を参照しているため、基準を満たすように目的を書き直すことができてしまう。これを防ぐのが、入力の I1・I2(機能を価値と利害関係者に結びつける)と、6.4 の対応表である。入力の形式を詰める理由は、ここにある。

### 8.2 `f` の入力テンプレートとのずれ

`g` の出力を `f` に渡すとき、3 点がずれる。

| 項目 | `f` の入力(現状) | `g` の出力 | 合わせ方 |
|---|---|---|---|
| アクションの呼び出し元 | `actions` に `caller` を持つ | 概念は呼び出し元を持たない。権限は同期に書く | `f` の側で、同期(`Request` を `when` に持つもの)から呼び出し元を導く。または、`f` のテンプレートから `caller` を外す |
| 事後条件 | `precondition` だけ | `requires` と `effects` の両方 | `f` に `effects` を加える。読み書きの量の見積もりは、事後条件が無いと出せない |
| 同期の条件 | `when` と `then` だけ | `where` を持つ | `f` に `where` を加える。条件は、読み取りの回数に効く |

1 点目は、形式の違いではなく、設計の考え方の違いである。概念に呼び出し元を書くと、概念が利用者の役割という別の概念に依存し、独立性の規則に反する。

### 8.3 詰める水準を決める規則

**規則: 次の写像の出力を変える情報は書く。変えない情報は書かない。**

これは、6.170 の「小さな事前設計」と同じ考え方である。厳密でありながら軽量な記法を使い、リスクに集中し、実装への偏りを避ける(講義 55 s7)。6.1040 も、含める細部と除く細部を分けている(L03)。

次の写像を `f` として、要素ごとに当てはめる。

| 要素 | 水準 | `f` の何を変えるか |
|---|---|---|
| 概念の名前と目的 | 必ず書く。各 1 文 | 作業の単位、コレクションの単位 |
| 原理 | 必ず書く。短い物語 1 つ | テストの筋書き(6.1040 assignment-4a は、原理をテストにする) |
| 状態 | 集合と関係の水準まで。属性の型は、振る舞いに効くものだけ | コレクションの構造、保存の量 |
| アクションの事前条件・事後条件 | 必ず書く。文でよい | セキュリティルール、読み書きの回数 |
| システムのアクション | 必ず書く | 時刻で動く処理の有無。サーバー側のコードが要るかどうか |
| 同期 | 概念をまたぐ本質的なものと、種類ごとの代表例 | 通知・権限・集計の方式 |
| 不変条件 | 競合や整合に関わるものだけ | 同じドキュメントに置くかどうか(6.1040 data-modeling) |
| UI、画面遷移 | 書かない | `g` の設定で除いている |
| アルゴリズム、内部の手順 | 書かない | 6.1040 L03 が除いている |
| 技術の名前 | 書かない | `g` の設定で除いている |

同期を網羅しないのは、資料の指示である。「網羅的に集める必要はない」が、概念をまたぐ本質的な着想と、アクセス制御や通知のような種類ごとの代表例は押さえる(6.1040 assignment-2。確認済み)。

詰める量は、リスクでも調整する。リスクは、失敗する確率と失敗の費用の積である(6.170 講義 55 s5)。新しく作った概念や、利用者が混乱しそうな概念は、厳密に書く。既知の概念は、名前と目的だけでも通じる。6.170 も、概念の記述では「自明なものと自明でないものを分け」、「新規な概念や混乱しやすい概念を正確に定義する」としている(講義 50 s13)。

## 9. 写像の手順

1. **入力の検証**: 各機能が I1〜I6 を満たすかを確かめる。満たさなければ、計算に進まず、欠けた箇所を返す。機能が大きすぎる・小さすぎる場合は `q` に差し戻す。
2. **目的の列挙**: 機能ごとに、応える必要を目的として書き出す。同じ必要は 1 つにまとめる。
3. **既知の概念の当てはめ**: 目的ごとに、既知の概念を探す。見つかれば、それを使う。
4. **新しい概念の設計**: 残った目的について、名前、目的、原理、アクション、状態の順に書く(6.1040 L03「コンセプトの設計方法」)。
5. **同期の設計**: 機能を実現するのに要る概念間のつながりを、同期として書く。対応表(6.4)を埋める。
6. **分割と統合**: 7.2 の表で違反を探し、操作を当てる。違反が無くなるまで繰り返す。目標どうしがぶつかって決められないときは、案を複数残す。
7. **制約の確認**: C1〜C5 を確かめる。
8. **出力**: 6.5 の形式で書く。残した案があれば、案ごとに出力し、違いを注記に書く。

手順 6 で複数の案を残す意味は、次の写像にある。モジュール性では優劣が付かない案でも、`f` のコストと開発工数では差が付くことがある。`f` は、通知の有無を両方計算して差を示す。同じ扱いを、概念の案にも使える。

## 10. 技術の選択(写像 h)と、候補の組み直し

技術基盤(Next や Nuxt などのフレームワーク、言語)の選択は、`g` の後、`f` の前に置く写像 `h` になる。手順は、スキル `concept-design-map` の `SKILL.md` に書いた。ここには、写像としての骨格だけを置く。この章の内容は、講義資料からは導けない。資料外である。

| 要素 | 内容 |
|---|---|
| 目的 | 概念の案ごとに、どの技術基盤で、どれくらいの工数で詳細設計と実装ができるかを出し、候補を並べること |
| 設定 | 見積もりの式(三点見積もり、実装主体の係数 `k`、統合の工数 `r`)。`f` の 4.2 と同じ式を使う |
| 入力 | `g` の出力(概念の案 2〜3 個 + 同期)と、`passthrough`(規模、予算、期限、実装主体、技術の希望) |
| 評価基準 | 工数(期待値と幅)、既製の部品で足りる割合、リスク、運用費 |
| 出力集合 | (概念の案, 技術基盤)の組のうち、概念の特徴から成り立つもの |

`h` と `g` の関係は、次の 3 点である。

- **`g` の分割・統合は、技術基盤に依存しない。** 4 章の「表現に依存しない」による。技術基盤を先に決めてから概念を分ける、という順にはしない。
- **`h` の結果は、`g` に差し戻せる。** 工数の大半を 1 つの概念が占めると分かったら、既知の概念で置き換えられないか、外せる機能を外せないかを、`g` に戻って調べる。これが「組み直し」である。
- **差し戻しても、`g` の制約は変えない。** 工数が減るからといって、概念が他の概念を参照する形にはしない。統合してよいのは、目的が同じ概念だけである(7.2)。

`h` を置くと、`f` の設定(現在は Next.js と Firebase を固定)は、`h` の出力になる。

見積もりの数値は、実測に基づかない仮置きである(スキルの `references/estimates.md`)。最初の 1 つの概念を作って測り、値を直す。

入力を作るための聞き取りは、同じフォルダの `interview-prompt.md` の指示書を使う。概念設計を知らない人から、5.4 と 6.5 の形式の成果物と、技術の希望を引き出す。

### 11.3 置き換えになる候補

ドメイン駆動設計(イベントストーミング、境界づけられたコンテキスト)は、`g` の前後ではなく、`g` そのものの代わりになる枠組みである(資料外)。分ける単位が概念より大きく、単位どうしの依存を認める点が違う。6.1040 は、機能を「オブジェクトではなく関心事を中心に」組織すると述べ、オブジェクト指向との混同を事例で扱っている(L04、modularity-case-studies)。併用すると、分ける単位が 2 種類になり、評価基準が混ざる。

### 11.4 推薦

- **前**: 6.1040 の問題設定を骨格にする。機能の `value` は、ジョブストーリーの書式で書く。
- **`g` の出力の検査**: 公理的設計の対応行列の考え方を、6.4 の対応表に使う。
- **後**: 個々の判断は「設計上の課題」の書式(問題 → 選択肢 → 採用案)で記録する。これは資料内にあり、意思決定写像の小さな版として使える。

理由は 2 つある。資料内の形式を骨格にすれば、講義を根拠に説明できる。資料外の枠組みは、資料が形式を定めていない箇所(機能の書式、対応表)にだけ使えば、評価基準が混ざらない。
